# SimpleNote 功能实现详解与问题分析

> 本文档基于对项目全部源码的逐行审阅，详细说明每个功能点的**实现机制**、**涉及的核心函数**，并指出**潜在问题**与**改进建议**。

---

## 一、笔记管理

### 1.1 创建笔记

#### 实现流程

```
前端 click "+ 新建笔记"
  → POST /api/notes  (JSON body: {title: "新建笔记"})
    → handlers_notes.go: handleCreateNote()
      → store.go: Store.createNote()
        ├── 读取 meta.json（readMetaLocked）
        ├── 生成 UUID（uuidString() → google/uuid.NewString()）
        ├── 创建 Note 结构体
        ├── 写入空内容文件（writeNoteLocked）
        ├── 追加到 meta.Notes 数组
        └── 写回 meta.json（writeMetaLocked）
  → 前端收到 {id, title, createdAt} 后跳转到 /note/:id
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 |
|------|------|------|
| `handleCreateNote` | `handlers_notes.go` | 73–86 |
| `Store.createNote` | `store.go` | 105–132 |
| `uuidString` | `utils.go` | 111–113 |
| `Store.writeNoteLocked` | `store.go` | 32–37 |
| `Store.writeMetaLocked` | `store.go` | 309–323 |
| `Store.readMetaLocked` | `store.go` | 289–307 |

#### 潜在问题

1. **竞态条件（低风险）**：`createNote` 中先创建 `.txt` 文件，再写 `meta.json`。如果两步之间进程崩溃，会产生"孤儿 `.txt` 文件"（有文件但 meta 中无记录）。虽然概率极低，但缺少事务性保证。
2. **默认标题不可配置**：硬编码 `"新建笔记"` 为默认标题，不支持国际化或自定义。
3. **无笔记数量限制**：虽然说"无限笔记"，但当笔记数量非常多时 `meta.json` 文件会变得很大，每次读写都是全量序列化。

### 1.2 编辑笔记内容（自动保存）

#### 实现流程

```
前端 textarea 输入
  → debounce(300ms) 触发
    ├── renderMarkdown()  // 实时渲染预览
    └── saveContent()    // 保存到服务端
         → POST /save/:id  (x-www-form-urlencoded: note={content})
           → handlers_notes.go: handleSaveNote()
             → store.go: Store.saveNoteContent()
               ├── 读取 meta.json 定位笔记
               ├── 写入新内容到 .txt 文件
               ├── 提取正文中的附件引用（extractAttachments）
               ├── 对比旧附件列表，删除已移除的附件文件
               ├── 更新 meta 中的 Attachments 字段
               ├── 更新 UpdatedAt 时间戳
               └── 写回 meta.json
         → 前端显示 "已保存" 状态提示
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|
| `debounce` | `note.ejs` JS | 143–149 | 通用防抖工具 |
| `renderMarkdown` | `note.ejs` JS | 95–101 | Marked + DOMPurify 渲染 |
| `saveContent` | `note.ejs` JS | 152–168 | XHR POST 保存 |
| `handleSaveNote` | `handlers_notes.go` | 121–133 | 后端保存处理 |
| `Store.saveNoteContent` | `store.go` | 190–225 | 含附件追踪逻辑 |
| `extractAttachments` | `store.go` | 377–386 | 正则提取 `/uploads/...` |
| `markNoteAsEdited` | `store.go` | 373–375 | 更新时间戳 |

#### 潜在问题

1. **保存频率过高**：防抖 300ms 虽然合理，但如果用户快速输入长篇 Markdown，每次保存都涉及 `读 meta → 写 .txt → 解析内容 → 对比附件 → 写 meta` 全流程，对于大量笔记的场景性能不佳。
2. **无版本控制**：每次保存都是覆盖写入，无法撤销到历史版本。用户误操作无法恢复。
3. **Ctrl+S 绕过防抖的对比**：`Ctrl+S` 直接调用 `saveContent()`，如果防抖定时器中还有待保存的内容，可能出现"旧内容覆盖新内容"的边缘情况（虽然 300ms 窗口较短，风险低）。
4. **保存失败无重试**：前端 `onerror` 只显示"网络异常"，没有自动重试逻辑。网络波动时用户可能丢失编辑内容。

### 1.3 笔记重命名

#### 实现流程

```
前端 title-input 输入
  → debounce(500ms) 触发 saveTitle()
    → PUT /api/notes/:id/title  (JSON body: {title: "新标题"})
      → handlers_notes.go: handleRenameNote()
        → store.go: Store.renameNote()
          ├── 读取 meta.json
          ├── 定位笔记索引
          ├── 更新 Title 字段（空值回退为 "无标题"）
          ├── 更新 UpdatedAt 时间戳
          └── 写回 meta.json
    → 前端更新 sidebar 中笔记链接文本 + 页面 title
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 |
|------|------|------|
| `saveTitle` | `note.ejs` JS | 171–191 |
| `handleRenameNote` | `handlers_notes.go` | 102–119 |
| `Store.renameNote` | `store.go` | 167–188 |
| `markNoteAsEdited` | `store.go` | 373–375 |
| `defaultString` | `utils.go` | 28–33 |

#### 潜在问题

1. **标题长度无限制**：前端虽然有 `max-width: 0` CSS 控制显示，但后端完全没有标题长度校验。恶意用户可以提交超长标题。
2. **特殊字符未过滤**：标题直接存入 JSON 和渲染到 HTML（模板中 `{{ .CurrentTitle }}` 已经做了 EJS 转义，所以 XSS 风险低），但如果标题包含特殊字符可能在某些场景下引发问题。
3. **500ms 防抖太长**：与内容保存的 300ms 不同，标题防抖设为 500ms，用户快速修改标题后立即切换笔记可能还未保存。

### 1.4 删除笔记

#### 实现流程

```
前端 hover 笔记项 → 显示 × 按钮
  → click ×
    → confirm("确定删除这个笔记吗？")
    → DELETE /api/notes/:id
      → handlers_notes.go: handleDeleteNote()
        → store.go: Store.deleteNote()
          ├── 读取 meta.json
          ├── 定位笔记索引
          ├── 遍历笔记的 Attachments 列表，逐个删除附件文件
          ├── 从 Notes 数组中移除该笔记
          ├── 写回 meta.json
          └── 删除 .txt 笔记文件
    → 前端：
        - 如果删除的是当前笔记 → 跳转首页 "/"
        - 否则直接从 DOM 中移除该笔记项
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 |
|------|------|------|
| `handleDeleteNote` | `handlers_notes.go` | 88–100 |
| `Store.deleteNote` | `store.go` | 134–165 |
| `Store.deleteAttachmentLocked` | `store.go` | 336–347 |
| `findNoteIndex` | `store.go` | 388–395 |

#### 潜在问题

1. **无软删除**：删除即永久删除，无回收站机制。对于重要笔记风险很高。
2. **删除附件失败时笔记仍会被删除**：`deleteNote` 中先删除附件再删除笔记文件。如果附件删除过程中某一步失败，会返回 error，但此时部分附件已被删除，状态不一致。应该改为：先完成所有验证再执行删除，或使用事务式回滚。
3. **前端无 AJAX confirm 的防误操作保护**：虽然用了 `confirm()`，但在移动端可能不够友好。此外 `confirm` 可以被通过浏览器设置屏蔽。

### 1.5 笔记列表与切换

#### 实现流程

**首次加载：**
```
GET / (已登录)
  → handlers_auth.go: handleHome()
    → Store.ensureLandingNote()
      ├── 读 meta.json
      ├── 若有笔记 → 按 UpdatedAt 排序 → 返回最近笔记 ID
      ├── 若无笔记 → 创建默认笔记（"新建笔记"）→ 返回 ID
    → Redirect → /note/:id
      → handlers_notes.go: handleNotePage()
        ├── getNoteContent(id) 获取笔记内容
        ├── listNotes() 获取所有笔记列表
        └── 渲染 note.ejs 模板（含侧边栏、编辑器、预览区）
```

**AJAX 切换：**
```
前端 click 侧边栏笔记项
  → fetchNoteContent(id, fallbackUrl)
    → GET /api/notes/:id/content
      → handlers_notes.go: handleNoteContent()
        → getNoteContent(id) → 返回 {id, title, content, createdAt, updatedAt}
    → 前端 updateNoteView(note)：
        - 更新 editor textarea
        - 更新 title-input
        - 更新 document.title
        - 设置 active 状态
        - renderMarkdown()
        - history.pushState 改变 URL（无刷新）
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 |
|------|------|------|
| `handleHome` | `handlers_auth.go` | 65–73 |
| `Store.ensureLandingNote` | `store.go` | 39–69 |
| `handleNotePage` | `handlers_notes.go` | 14–39 |
| `handleNoteContent` | `handlers_notes.go` | 41–61 |
| `Store.getNoteContent` | `store.go` | 71–91 |
| `Store.listNotes` | `store.go` | 93–103 |
| `sortNotesByUpdatedAt` | `store.go` | 360–371 |

#### 潜在问题

1. **`window.location.reload()` 在 popstate 中被调用**（`note.ejs:273`）：用户使用浏览器后退/前进按钮时会触发整页刷新，而非 AJAX 加载体验。这是因为 `fetchNoteContent` 使用 `pushState` 改变 URL，但浏览器历史回退时没有对应的 AJAX 处理，只能整页刷新。
2. **首页每次都触发 `ensureLandingNote`**：即使已有笔记，该函数每次都要读 meta 并排序。如果笔记数量很多会有性能开销。

## 二、Markdown 渲染

### 2.1 实时渲染机制

#### 实现流程

```
编辑器 textarea 内容变更
  → debounce(300ms) 或用户主动触发
    → renderMarkdown()
      ├── marked.parse(editor.value)    // Marked.js 解析
      └── DOMPurify.sanitize(rendered)  // XSS 净化
      → preview.innerHTML = 净化后的 HTML
```

#### 涉及的关键代码

| 位置 | 代码 | 作用 |
|------|------|------|
| `note.ejs:96` | `marked.parse(editor.value)` | Markdown → HTML |
| `note.ejs:97-99` | `DOMPurify.sanitize(rendered, {USE_PROFILES: {html: true}})` | HTML 净化 |
| `note.ejs:57` | `<textarea id="editor" spellcheck="false">` | 原始 Markdown 编辑区 |
| `note.ejs:58` | `<div id="preview">` | 渲染预览区 |

#### 潜在问题

1. **DOMPurify 配置过严/过松**：`USE_PROFILES: {html: true}` 使用 DOMPurify 的标准 HTML 配置，但没有额外允许 Markdown 中常见的自定义属性（如 `data-*`）。对于某些 Markdown 扩展语法可能会被意外清除。
2. **Marked.js 无配置**：直接使用 `marked.parse()`，没有启用任何 Marked 扩展（如 GFM 表格、任务列表、脚注等）。依赖 Marked.js 的默认行为，可能随版本变化。
3. **客户端渲染安全依赖**：XSS 防护完全依赖 DOMPurify 的客户端净化。如果存在绕过 DOMPurify 的 0-day，系统将面临风险。建议在服务端也做一层净化或至少对输出做转义。
4. **无代码高亮**：Markdown 代码块没有集成 highlight.js 等语法高亮库，代码块仅以纯文本显示。

## 三、附件上传

### 3.1 上传流程

#### 实现流程

```
前端点击上传按钮 → 选择文件
  → file-input change 事件
    ├── 前端校验：file.size > 10MB → alert 拦截
    → POST /api/upload (multipart/form-data: file, noteId)
      → handlers_notes.go: handleUpload()
        ├── c.FormFile("file") 获取上传文件
        ├── 服务端二次校验：file.Size > 10MB → 返回 400
        ├── os.MkdirAll(uploadsDir) 确保上传目录存在
        ├── 生成存储名：uuid.NewString() + strings.ToLower(原扩展名)
        ├── c.SaveUploadedFile(file, destination) 保存文件
        ├── 若 noteId 非空 → store.addAttachment(noteId, storedName) 记录到 meta
        ├── 判断文件是否为图片（imagePattern 正则）
        └── 返回 JSON: {success, url, filename, originalname, markdown}
    → 前端在光标位置插入 markdown 链接
    → 自动触发 renderMarkdown + saveContent
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|
| `handleUpload` | `handlers_notes.go` | 135–181 | 上传处理 |
| `Store.addAttachment` | `store.go` | 227–243 | 关联附件到笔记 |
| `attachmentPattern` | `models.go` | 21 | 匹配 `/uploads/uuid.ext` |
| `imagePattern` | `models.go` | 22 | 判断图片扩展名 |
| `maxUploadSize` | `models.go` | 16 | 10MB 上限 |

#### 潜在问题

1. **文件类型未校验**：仅通过正则判断扩展名来区分图片和普通文件，没有检查文件 MIME type 或 magic number。攻击者可以伪造扩展名上传恶意文件。
2. **上传文件名风险**：`originalName` 直接用于生成 Markdown 链接文本 `[originalName](url)`。如果原始文件名包含 `]` 或其他特殊字符，会破坏 Markdown 语法。虽然不影响安全性，但会产生格式错误。
3. **附件清理的时序问题**：`saveNoteContent` 中会根据当前正文内容清理已移除的附件引用。如果用户 A 在编辑中删除了附件引用并保存，此时附件文件被删除。但如果另一个标签页还引用该附件，会出现"图片 404"的情况。这是多标签页场景的一致性问题。
4. **`addAttachment` 中 noteID 不存在时静默返回 nil**：当上传时 noteId 对应的笔记不存在，函数返回 `nil`（无错误），但附件文件已经保存到磁盘。这会产生孤立的附件文件，永远不会被清理。
5. **上传目录无自动清理**：孤立附件（如上述情况）没有定期清理机制。

## 四、用户认证

### 4.1 JWT 认证机制

#### 实现流程

```
登录请求：
  POST /login  (password + rememberMe)
    → handlers_auth.go: handleLogin()
      ├── 比对密码：password != a.password
      ├── signAuthToken(remember) → 签发 JWT
      ├── 设置 Cookie：
      │   ├── Name: "auth_token"
      │   ├── HttpOnly: true
      │   ├── SameSite: Strict
      │   ├── Path: /
      │   ├── Secure: false (本地开发友好，但生产环境应开启)
      │   ├── MaxAge: 30天 (仅 rememberMe=true 时)
      │   └── Expires: time.Now() + 30天
      └── Redirect → "/"

鉴权中间件：
  requireAuth()
    ├── 从 Cookie 中读取 auth_token
    ├── verifyAuthToken(token)
    │   ├── 验证签名算法必须为 HS256
    │   ├── 使用 jwtSecret 验证签名
    │   └── 检查 Token 是否过期
    ├── 若无效 →
    │   ├── API 请求 (wantsJSON) → 401 JSON {"success": false, "message": "Unauthorized"}
    │   └── 浏览器请求 → 302 Redirect → /login
    └── 若有效 → c.Set("user", claims) → c.Next()
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|
| `handleLogin` | `handlers_auth.go` | 21–49 | 登录处理 |
| `handleLogout` | `handlers_auth.go` | 51–63 | 登出处理 |
| `handleLoginPage` | `handlers_auth.go` | 10–19 | 登录页渲染 |
| `requireAuth` | `auth.go` | 12–28 | 鉴权中间件 |
| `claimsFromContext` | `auth.go` | 30–37 | 从请求提取 JWT Claims |
| `verifyAuthToken` | `auth.go` | 39–59 | JWT 验证 |
| `signAuthToken` | `auth.go` | 61–74 | JWT 签发 |
| `parseJWTExpiresIn` | `utils.go` | 72–109 | 有效期解析 |

#### 潜在问题

1. **Cookie `Secure: false`**（`handlers_auth.go:41`）：即使在 HTTPS 环境下，Cookie 也不会被标记为 Secure。这意味着 Cookie 可能通过 HTTP 明文传输，存在被中间人截获的风险。建议根据请求是否为 HTTPS 动态设置此值，或通过环境变量控制。
2. **密码以明文比对**：`password != a.password` 直接比较明文。如果数据库（meta.json）泄露且密码被猜测，安全性较低。建议至少加入 `bcrypt` 哈希存储。（虽然当前密码存在环境变量中而非文件，但作为防御纵深仍值得考虑。）
3. **JWT Secret 一旦泄露全部作废**：所有用户共用同一个 `JWT_SECRET`，一旦泄露需要所有用户重新登录。
4. **无登录失败次数限制**：没有暴力登录防护。攻击者可以无限次尝试密码。建议添加 rate limiting 或指数退避。
5. **登出后旧 Token 仍然有效**：JWT 是无状态的，一旦签发，在过期前始终有效。登出只是清除了 Cookie，但 Token 本身无法在服务端作废（除非引入 Token 黑名单机制）。
6. **`detectBaseDir` 逻辑**（`utils.go:43-61`）：运行时通过探测 `views/` 和 `public/` 目录来定位资源路径。这虽然灵活，但在 Release 构建中如果资源目录结构不一致可能导致找不到模板。

## 五、错误处理

### 5.1 统一错误渲染

#### 实现流程

```
各 handler 中出错时：
  a.renderError(c, statusCode, title, message, action)
    → 判断 wantsJSON(c)：
        ├── true → c.JSON(statusCode, {success: false, message: ...})
        └── false → 
            → 判断 wantsHTML(c)：
                ├── true → c.HTML(statusCode, "error.ejs", {
                │     StatusCode, Title, Message, ActionHref, ActionText, AppName
                │   })
                └── false → c.String(statusCode, message)

Gin 全局错误处理：
  router.NoRoute → renderError(404, ...)
  router.NoMethod → renderError(405, ...)
  gin.CustomRecovery → panic 恢复 → renderError(500, ...)
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|
| `renderError` | `errors.go` | 5–30 | 统一错误渲染 |
| `defaultErrorAction` | `errors.go` | 32–37 | 默认错误跳转逻辑 |
| `wantsJSON` | `utils.go` | 15–22 | 判断是否为 API 请求 |
| `wantsHTML` | `utils.go` | 24–26 | 判断是否为浏览器请求 |
| `gin.CustomRecovery` | `router.go` | 15–18 | Panic 恢复 |

#### 潜在问题

1. **`wantsJSON` 判断逻辑过于宽泛**（`utils.go:15-22`）：任何 `Accept` 头包含 `application/json` 的请求都会被认为是 API 请求，即使该请求是浏览器发出的。此外，所有 `/save/*` 路径也被强制判为 JSON。这意味着如果用户在浏览器中直接访问 `/save/xxx`（GET 请求），会得到 JSON 错误而非 HTML 错误页。
2. **错误信息可能泄露内部信息**：`CustomRecovery` 中 `log.Printf("panic recovered: %v", recovered)` 会将 panic 信息打印到日志。如果 panic 中包含敏感信息，可能被日志收集系统捕获。
3. **错误页无分类**：所有 404 都显示"页面不存在"，对于笔记不存在和路由不存在使用同一个错误页，用户难以区分。
4. **`wantsHTML` 判断条件过窄**：仅检查 `Accept` 头中是否包含 `text/html`。Gin 的 EJS 渲染场景下浏览器通常会发送此头，但某些 HTTP 客户端（如 curl）可能不发送。

## 六、数据存储

### 6.1 文件系统存储模型

#### 实现流程

```
启动时：
  Store.bootstrap()
    ├── ensureNotesDirLocked() → os.MkdirAll(notesDir)
    ├── os.MkdirAll(uploadsDir)  
    └── migrateOldNotesLocked() → 迁移旧版 1.txt ~ 8.txt 格式

每次读写：
  所有操作遵循：
    1. store.mu.Lock() 加互斥锁
    2. readMetaLocked() → os.ReadFile(meta.json) + json.Unmarshal
    3. 业务逻辑处理
    4. writeMetaLocked() → json.MarshalIndent + os.WriteFile(meta.json)
    5. store.mu.Unlock() 释放锁
```

#### 涉及的核心函数

| 函数 | 文件 | 行号 | 说明 |
|------|------|------|------|
| `bootstrap` | `store.go` | 14–26 | 启动初始化 |
| `readMetaLocked` | `store.go` | 289–307 | 读 meta.json |
| `writeMetaLocked` | `store.go` | 309–323 | 写 meta.json |
| `readNoteContentLocked` | `store.go` | 325–334 | 读笔记内容 |
| `notePath` | `store.go` | 349–351 | 拼接笔记文件路径 |
| `migrateOldNotesLocked` | `store.go` | 245–287 | 旧数据迁移 |

#### 潜在问题

1. **meta.json 全量读写**：每次任何笔记的任何变更（创建、重命名、保存、删除）都会读取并重写整个 `meta.json`。当笔记数量达到数千条时，这将成为显著的性能瓶颈。
2. **互斥锁粒度过大**：全局一把 `sync.Mutex`，所有笔记操作都串行执行。如果一个请求正在保存大笔记，其他所有请求都要等待。在多用户并发场景下会成为严重瓶颈。
3. **meta.json 写入非原子**：`os.WriteFile` 直接覆盖写入，如果写入过程中断电或崩溃，文件可能被截断为 0 字节，导致所有笔记元数据丢失。应使用「写临时文件 + rename」的原子写入模式。
4. **无文件系统权限校验**：启动时没有检查 `notes/` 和 `uploads/` 目录的读写权限，如果权限不足会在第一次写入时才报错。
5. **`migrateOldNotesLocked` 硬编码迁移范围**：只迁移 `1.txt ~ 8.txt`，如果旧版本用户有超过 8 个笔记，超出的不会被迁移。

### 8.1 Docker 部署

#### 实现流程

```
Dockerfile（多阶段构建）：
  阶段 1 (builder)：
    FROM golang:1.25.8-alpine
    WORKDIR /home/app
    COPY go.mod go.sum → go mod download

  阶段 2 (runner)：
    FROM alpine:3.22
    RUN apk add ca-certificates tini
    COPY --from=builder /simplenote ./
    COPY public ./public
    COPY views ./views
    ENTRYPOINT ["/sbin/tini", "--"]
    CMD ["./simplenote"]

docker-compose.yml：
  ports: 13000:3000
  volumes: ./data:/home/app/notes, ./uploads:/home/app/uploads
  restart: always
  environment: PASSWORD, JWT_SECRET
```

#### 涉及的关键配置

| 文件 | 行号 | 说明 |
|------|------|------|
| `Dockerfile:1-35` | 全文件 | 多阶段构建 |
| `docker-compose.yml:1-14` | 全文件 | Compose 编排 |
| `.github/workflows/docker-build.yml` | 全文件 | CI/CD 工作流 |

#### 潜在问题

1. **README 与实际工作流不一致**：README 中声明有两个工作流（`docker-build.yml` 和 `release.yml`），但实际上只有一个 `docker-build.yml` 文件，它同时负责测试、构建、打包和 Release。README 需要更新。
2. **Docker Compose 端口映射**：宿主机端口 `13000` 映射到容器 `3000`，但 `PORT` 环境变量默认值为 `3000`。如果用户修改了容器内端口，需要同步修改 compose 映射。
3. **无 health check**：Docker Compose 没有配置 `healthcheck`，Docker 无法判断应用是否健康。
4. **无资源限制**：没有设置 `mem_limit`、`cpus` 等资源限制。
5. **`restart: always`**：容器退出时总是重启，包括配置错误导致的启动失败场景。应考虑使用 `unless-stopped`。
6. **MIPS 交叉编译特殊配置**：`linux_mipsle` 目标使用了 `CGO_ENABLED=0 GOOS=linux GOARCH=mipsle GOMIPS=softfloat` 和 `-tags="netgo osusergo"`。这是为了在 MIPS 设备上纯 Go 实现网络和用户查询，但缺少对 MIPS 架构的说明。

## 十、总结

SimpleNote 是一个架构简洁、功能完整的 Markdown 笔记应用。它的优势在于：

- **极简架构**：无数据库、零依赖服务，文件即数据
- **安全性基础扎实**：JWT + HttpOnly Cookie + DOMPurify 净化
- **用户体验良好**：自动保存、实时预览、响应式设计
- **部署友好**：Docker Compose 一键启动，多平台编译

主要改进方向集中在：

1. **数据完整性**：原子写入、事务式删除
2. **安全性增强**：Secure Cookie、bcrypt 密码哈希、上传文件类型校验、rate limiting
3. **性能优化**：减少 meta.json 读写频率、缩小锁粒度
4. **移动端体验**：允许预览模式、优化交互
5. **可维护性**：补充国际化、完善文档、添加健康检查
